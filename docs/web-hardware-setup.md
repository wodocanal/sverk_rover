# Настройка оборудования через веб

**Калибровка моторов** и **Device Manager** доступны только в разделе **Настройки**.
Это операции с реальным оборудованием: используйте веб только в доверенной
сети и не предоставляйте доступ посторонним. Программная кнопка остановки
не заменяет физическое отключение питания моторов.

## Установка обновления

После переноса исходников на ровер соберите новые интерфейсы и пакеты:

```bash
cd ~/sverk_rover
sudo systemctl stop rover-web
sudo systemctl stop rover-bringup
source /opt/ros/jazzy/setup.bash
colcon build --packages-up-to rover_web rover_bringup
# Только после успешной сборки:
deploy/systemd/install.sh
sudo systemctl start rover-bringup
sudo systemctl start rover-web
```

Сначала остановите движение и сохраните карту. Пример для обычного install;
если workspace собран с --symlink-install, сохраняйте этот режим.
Не смешивайте режимы. [Обновление и резервные копии](operations.md).

Установщик сохраняет существующие `/etc/default/rover-*`. Он устанавливает
узкое правило Polkit и резервное правило sudoers: пользователю сервисов
разрешается `start`/`stop` юнита `rover-bringup.service` и только `restart`
для `rover-web.service`. Произвольные команды, shell, daemon-reload и управление
другими юнитами не разрешаются этим правилом. Уже имеющиеся права пользователя
оно не отменяет. Веб-кнопка перезапуска bringup выполняет stop, затем start.
Сам веб остаётся непривилегированным процессом. При отказе авторизации systemctl
вызывается через `sudo -n` с точно разрешёнными аргументами, без запроса пароля.
Ошибки запуска самого сервиса и таймауты не вызывают повтор команды.

### Исправление Interactive authentication required

Это означает, что пользователь процесса веба не получил права на управление
systemd. `git pull` и `colcon build` сами не устанавливают системные разрешения.
Не нужно передавать пароль Linux-пользователя веб-приложению или запускать весь
веб от root. На ровере через SSH из папки проекта выполните один раз:

```bash
sudo bash deploy/systemd/install-service-control.sh
```

Пароль администратора, если требуется, вводится в терминале. Установщик читает
`User` существующего `rover-web.service`, проверяет пользователя и синтаксис
через `visudo`, устанавливает `/etc/sudoers.d/rover-service-control` с владельцем
root и правами 0440. Он проверяет разрешения через `sudo -l`, не выполняя
запусков или остановок. Переустановка сервисов и изменение профиля не нужны.

Если пользователь задан нестандартно или веб пока запущен вручную, его можно
указать явно (он должен совпадать с реальным пользователем веб-процесса):

```bash
sudo env ROVER_SERVICE_USER=pi bash deploy/systemd/install-service-control.sh
```

Для применения нового кода пересоберите `rover_web`, затем один раз выполните
`sudo systemctl restart rover-web`. После установки прав уже обновлённому вебу
достаточно обновить состояние: проверка разрешений кэшируется на 10 секунд.
Далее кнопки работают без ввода пароля. На главной странице раздел
**Права управления сервисами** показывает пользователя веба, результат
проверки sudo и команду настройки. Отрицательная проверка sudo не исключает
доступ через ранее установленное правило Polkit.

Если ошибка сохраняется, проверьте `systemctl show rover-web -p User`,
`sudo visudo -c`, journalctl сервиса и пользовательские systemd-ограничения
`NoNewPrivileges`/`RestrictSUIDSGID`, которые могут запрещать sudo.
Скрипт требует установленного `sudo` и Linux с systemd; на macOS и в обычном
Docker эти системные кнопки не работают. Не выставляйте веб в публичную сеть:
доступ к интерфейсу позволяет управлять двумя сервисами без отдельного логина.

Для Device Manager веб должен работать отдельным сервисом `rover-web`.
При запуске веба внутри самого bringup остановка bringup остановит и веб.

## Сервисы на главной странице

На **Главной** находится блок **Сервисы ровера**. Состояние читается напрямую
из systemd и обновляется автоматически. Для bringup есть переключающаяся
кнопка **Запустить / Остановить** и отдельная **Перезапустить**. Для веба
доступен только **Перезапустить веб**, без кнопок запуска и остановки.

Каждая операция требует подтверждения. Во время запуска/остановки кнопки
блокируются. Если systemd или unit-файлы недоступны, интерфейс показывает
причину и не имитирует работу сервисов. В локальном Docker без systemd эти
кнопки недоступны. Перезапуск веба также недоступен, если текущий процесс
запущен вручную, а не внутри `rover-web.service`.

Перед перезапуском веба останавливаются его навигация, маршрут и ручное
движение. Активную настройку Device Manager сначала нужно сохранить или
отменить. Команда перезапуска передается systemd после ответа браузеру,
браузер ожидает новый идентификатор процесса до 90 секунд и перезагружает
страницу. При отказе и Polkit, и ограниченного sudo показывается инструкция.
При недоступности сервера
после таймаута нужно проверить `systemctl status rover-web` на ровере.

## Калибровка моторов

1. Надежно установите ровер на подставку: все четыре колеса должны быть
   в воздухе. Не держите ровер в руках, уберите провода от колес.
2. Остановите навигацию, патрулирование и любые внешние источники движения.
   Сам `base_driver_node` должен работать и получать данные энкодеров.
3. Подтвердите условия безопасности и нажмите **Начать калибровку**.
4. Нажмите **Прокрутить этот мотор**. Команда идет на один физический канал,
   обходя старую перестановку. Скорость ограничена 0,06 м/с, длительность
   2 секундами. Между шагами остальные моторы не включаются автоматически.
5. Дождитесь остановки. Выберите, какое колесо вращалось и катило бы оно
   ровер вперед или назад. Лево/право определяются относительно переда ровера.
   Это не универсальное «по часовой стрелке»: оно зависит от стороны наблюдения.
6. Подтвердите выбор и повторите для остальных трех каналов. Повторное
   назначение одного колеса двум каналам запрещено. Если мотор не вращался
   или двигалось несколько энкодеров, проверьте проводку и повторите тест.
7. Нажмите **Сохранить калибровку**, затем **Применить: перезапустить bringup**.

Сохраняются четыре массива: `motor_command_order`, `motor_command_signs`,
`encoder_feedback_order`, `encoder_feedback_signs`. Порядок команды задается
от физических каналов к колесам, обратная связь — от колес к каналам энкодеров;
эти перестановки в общем случае не одинаковы. Знак обратной связи определяется
из изменения счетчика энкодера и указанного оператором направления движения.

Файл по умолчанию: `~/.config/sverk-rover/motor_calibration.json` пользователя,
под которым работает драйвер. Параметр `motor_calibration_file` находится в
`rover_base_driver/config/base.yaml`. При запуске драйвера сохраненные значения
имеют приоритет над четырьмя массивами YAML. Некорректный файл не применяется
молча: запуск драйвера завершится ошибкой. Предыдущая версия сохраняется как
`motor_calibration.json.bak`; после восстановления также нужен перезапуск.

Изменения не применяются к текущей одометрии на ходу: применяется весь набор
при перезапуске bringup. До этого действует предыдущая схема.

### Остановка и обрыв связи

- В активной калибровке драйвер игнорирует `cmd_vel` независимо от источника.
- Двухсекундный таймер находится в драйвере: закрытие вкладки не оставляет
  бесконечную команду вращения. Потеря энкодерных данных прерывает тест.
- **Остановить мотор** и общая кнопка Stop прерывают текущий импульс.
- После импульса или закрытия вкладки режим калибровки остается активным,
  чтобы обычное движение не возобновилось неожиданно.
- **Завершить без применения** снимает блокировку и оставляет текущие рабочие
  параметры. Уже сохраненный файл не удаляется: он загрузится при перезапуске.
  Перед снятием блокировки отключите внешние команды движения.

ROS API: `/drive/calibrate_motors`, тип `rover_interfaces/srv/CalibrateMotors`.
Команды: `status`, `begin`, `pulse`, `record`, `save`, `stop`, `end`.
`wheel`: 0 FL, 1 FR, 2 RL, 3 RR; `direction`: +1 вперед, -1 назад.
`begin` требует `wheels_raised=true`.

## Device Manager

Мастер использует те же протокольные проверки, что и консольный `setup_devices`:
Quad-MD, Yahboom YB-MRA02-V1.0, SLLIDAR/RPLIDAR. Для лидара сначала используется
официальный SDK, при неудаче — прямой запрос информации. Камера, LED, Octoliner
и голосовой модуль не входят в этот последовательный мастер.

1. Нажмите **Режим обслуживания: остановить bringup** и подтвердите действие.
   Веб остановит собственную навигацию и маршрут, затем аппаратный сервис.
   Драйверы, запущенные вручную вне сервиса, нужно остановить отдельно.
2. Отключите USB контроллера, IMU и лидара. Другие serial-устройства можно
   оставить: они попадут в исходный список и не будут кандидатами.
3. Подтвердите подготовку и нажмите **Начать настройку**.
4. Подключите один компонент, выберите его роль и новый порт. Нажмите
   **Проверить устройство**, дождитесь результата и **Принять найденное устройство**.
5. Оставляйте принятые компоненты подключенными и повторите для остальных.
6. Нажмите **Сохранить конфигурацию устройств**, затем **Запустить bringup**.

Во время проверки занятые порты и видимые аппаратные драйверы блокируют мастер.
Веб не принимает неподтвержденную IMU автоматически: ошибка остается видимой,
можно проверить подключение и повторить. Отмена во время проверки ждет завершения
текущей ограниченной по времени процедуры и отбрасывает результат; новый запуск
оборудования до ее завершения запрещен.

Старый файл не изменяется до завершения всех трех проверок и явного сохранения.
Сохраняются стабильные пути, aliases, USB-идентичность, baudrate, профиль,
параметры и результат проверки. После запуска bringup Device Manager сам
восстанавливает ссылки в runtime-каталоге с учетом этих данных.

Путь берется из `rover_device_manager/config/device_manager.yaml`, обычно
`~/.config/rover/devices.json`. При нестандартном пути запуска bringup задайте
тот же путь ROS-параметром веба `device_setup_config`. Веб показывает полный
путь файла; его пользователь должен совпадать с пользователем bringup.
Предыдущий файл сохраняется в `devices.json.bak`. Внешнее изменение файла
во время мастера блокирует сохранение, чтобы не затереть чужие изменения.

## Проверки без оборудования

Модульные тесты находятся в `rover_base_driver/test/test_motor_calibration.py`
и `rover_device_manager/test/test_web_setup.py`. HTTP/ROS-тест в
`rover_web/test/test_maintenance_integration.py` заменяет serial-контроллер
имитацией в памяти и проверяет весь цикл, запрет движения и общую остановку.
Он не подтверждает работу конкретной прошивки, физическую проводку и качество
обнаружения реального USB-оборудования. Это требует отдельной проверки на ровере.
