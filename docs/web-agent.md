# Агент в веб-интерфейсе

## Связь с сервером

На странице есть отдельный индикатор MQTT-связи с сервером коммуникации.
Мост `fleet_text_bridge_ros2` раз в секунду публикует `std_msgs/String` с JSON
в `/fleet/connection`. Зелёный статус появляется после CONNACK, успешного SUBACK
на топик команд и PUBACK публикации online. Адрес брокера и Robot ID берутся из
фактических параметров моста; логины, пароли и токены не публикуются.

Веб обновляет индикатор автоматически и по кнопке «Обновить». Если сообщения
не приходят более 5 секунд или издатель исчез, зелёный статус снимается.
Если мост старой версии не публикует heartbeat, отображается отсутствие данных,
а не утверждение об исправном соединении. Необходимо обновить и мост, и веб.
Имена задаются через `connection_topic` моста и `fleet_connection_topic` веба;
основные конфиги используют общий реестр топиков.

Проверяется MQTT-транспорт, а не HTTP API языковой модели и не работоспособность
самого приложения коммуникационного сервера. Подтверждение брокером подписки
не заменяет проверку полного цикла реальной команды. Кнопка обновления не
отправляет агенту тестовых команд и не вызывает движение.

Страница **Агент** отправляет команды уже запущенной ноде агента и показывает
ее статусы, ответы и ошибки. Она не запускает агента, MCP или языковую модель.
Команды могут приводить к реальному движению: используйте интерфейс только
в доверенной сети и при безопасном положении ровера.

Топики задаются в `rover_web/config/web.yaml`: `agent_input_topic`,
`agent_answer_topic`, `agent_status_topic`. Основной конфиг ссылается на общий
реестр `rover_interfaces/config/topics.yaml`, как и конфиг агента.
При ROS remapping или отдельных переопределениях агента настройте веб на те же
фактические имена. По умолчанию это `/agent/text_command`, `/agent/answer`,
`/agent/status`, тип всех трех топиков: `std_msgs/msg/String`.

Вход: JSON `{"message_id": "UUID", "text": "сообщение"}` в поле `data`.
Robot ID не подменяется вебом: агент использует свою настроенную идентичность.
Ответы сопоставляются по `message_id`. Поддерживаются также обычные текстовые
ответы. Ответы на внешние запросы видны с отдельной отметкой.

История общая для клиентов веб-сервиса, хранится только в памяти (100 запросов)
и очищается при его перезапуске. До запуска веба сообщения не восстанавливаются.
Это не диалоговая память модели: агент обрабатывает каждый запрос отдельно.
Наличие подписчика на вход не гарантирует исправность модели или MCP.
Статус «Отправлено» означает только публикацию в ROS, не выполнение команды.
Автоматических повторных отправок нет; UUID защищает от повторной публикации
при ручном повторе того же запроса, пока запись остается в истории веба.

HTTP: `GET /api/agent` возвращает историю и состояние ROS-соединений;
`POST /api/agent/send` принимает `text` (1–4000 символов) и `message_id` (UUID).
Пока активна калибровка моторов, отправка из веб-чата блокируется.

## Настройки подключения к серверу

На странице **Настройки → Общие → Подключение к серверу** доступны адрес
MQTT-брокера, порт, префикс топиков, логин и пароль. Robot ID показывается только
для чтения: его необходимо менять согласованно с идентичностью агента, а не
отдельно в транспортном мосте. Это не настройки API модели.

- **Сохранить** записывает значения, не разрывая действующее соединение.
- **Сохранить и переподключить** сохраняет значения и вызывает ROS-сервис
  `/fleet_text_bridge/reconnect` (`std_srvs/srv/Trigger`). Меняется только
  MQTT-клиент, ROS-нода, агент, MCP и остальной bringup не перезапускаются.
- Если мост выполняет команду или имеет очередь, переподключение отклоняется.
  Настройки остаются сохранёнными; повторите переподключение после завершения.
- Если мост выключен, сохранение доступно, но переподключение не запускает
  ноду автоматически. Сохранённые значения загрузятся при её следующем запуске.
- Успешный ответ сервиса означает начало попытки соединения, а не подтверждение
  доступности сервера. Проверяйте индикатор на странице агента или в настройках.

Файл `~/.config/sverk-rover/fleet_connection.json` принадлежит пакету
`fleet_text_bridge_ros2` и содержит локальные переопределения параметров.
Он записывается атомарно с правами `600`, находится вне репозитория и переживает
перезапуск ноды, systemd-сервиса и обновление кода. Приоритет:
сохранённые веб-настройки выше стартовых ROS-параметров (конфиг пакета/окружение).
Без этого файла сохраняется прежняя схема конфигурации.

Пустое поле пароля сохраняет прежний пароль. Если пароль никогда не сохранялся,
мост использует `mqtt_password_env` (по умолчанию `FLEET_MQTT_PASSWORD`). Галочка
удаления сохраняет явно пустой пароль и отключает этот fallback. Пароль не
возвращается в HTTP-ответах и не записывается в журнал действий; он хранится
в файле открытым текстом, поэтому доступ к файлу должен иметь только владелец.
Вводите пароль только в доверенной сети или через защищённый туннель: текущие
HTTP-интерфейс и MQTT-транспорт сами по себе шифрование не добавляют.

Веб и мост должны работать под одним пользователем либо иметь доступ к одному
явно заданному файлу. Параметры пути: `fleet_settings_file` у веба и
`connection_settings_file` у моста. Параметр веба `fleet_bridge_node_name`
по умолчанию равен `/fleet_text_bridge`. При несовпадении путей кнопка
переподключения недоступна. После обновления впервые пересоберите оба пакета
и перезапустите соответствующие сервисы; далее достаточно кнопки в вебе.

HTTP: `GET /api/server/settings` возвращает безопасные настройки и состояние;
`POST /api/server/settings` принимает объект `settings` с полями `mqtt_host`,
`mqtt_port`, `mqtt_topic_prefix`, `mqtt_username` и необязательным `mqtt_password`,
а также флаги `clear_password` и `reconnect`.
